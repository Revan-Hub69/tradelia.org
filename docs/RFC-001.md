# RFC-001 — Tradelia Crypto Futures Engine

Versione: 1.0  
Stato: Design definitivo  
Obiettivo: sistema deterministico, accademicamente solido (2025), estendibile, auditabile, capace di execution futures con leva e gestione posizione dinamica usando solo dati gratuiti.

## 0. Principi non negoziabili

**Determinismo**  
A parità di input → stesso output.  
L’AI non può modificare direttamente decisioni di trading senza guardrail.

**Auditabilità totale**  
Ogni trade deve essere riproducibile offline (demo/replay).

**Feature-centric design**  
I dati raw sono ingestione → features persistite.  
Le strategie leggono solo features.

**Universo ampio, rischio controllato**  
Nessuna esclusione “per principio”.  
Si gestisce il rischio con tiering, non con censure.

**HFT-aware, non HFT-fake**  
Architettura event-driven + microstruttura corretta.  
Niente promesse impossibili.

## 1. Architettura a strati (immutabili vs estendibili)

### 1.1 Strati IMMUTABILI (non si rifanno mai)

```
┌─────────────────────────────┐
│  Strategy Kernel            │  ← deterministico, versionato
├─────────────────────────────┤
│  Feature Store              │  ← solo features, no raw infinito
├─────────────────────────────┤
│  Data Quality & Sync Layer  │  ← gate 0
├─────────────────────────────┤
│  Execution Engine / OMS     │
├─────────────────────────────┤
│  Audit & Replay Layer       │
└─────────────────────────────┘
```

### 1.2 Strati ESTENDIBILI (plug-in)

- nuove fonti dati (options, on-chain, sentiment)
- nuove feature
- nuovi exchange
- AI modules (solo come feature / advisory)

## 2. Universo strumenti (NO universe ristretto)

### 2.1 Universe Builder (deterministico)

**Input**

- Binance exchangeInfo (perpetual USDT)
- volume, spread, depth, OI, funding, volatility

**Output**

- `symbol_universe[]`

### 2.2 Liquidity & Risk Tiering

| Tier | Descrizione        | Ammesso | Restrizioni                     |
|------|--------------------|---------|---------------------------------|
| A    | alta liquidità     | sì      | leva piena                      |
| B    | media              | sì      | leva ridotta                    |
| C    | bassa              | sì      | size & leva fortemente ridotte  |

**Regola chiave:** nessuna coin esclusa, ma leva e sizing dipendono dal tier.

## 5. Strategy Kernel (DETERMINISTICO)

### 5.1 Gate 0 — Data Quality

Blocca tutto se:

- feed desync
- missing L2
- latenza > soglia

### 5.2 Gate 1 — Regime

Classificazione:

- trend
- range
- high-vol
- squeeze / deleverage

Usa:

- returns
- vol
- funding + OI

### 5.3 Gate 2 — Setup

Setup ammessi (1 attivo per symbol):

- breakout
- pullback
- mean-revert

Conferme:

- order flow
- L2 imbalance
- spread/resilienza

### 5.4 Gate 3 — Execution & Risk Plan

#### 5.4.1 Leva dinamica (formula base)

```
risk_usd = equity * risk_pct

stop_dist = max(
  ATR * k,
  structure_stop + micro_buffer
)

position_size = risk_usd / stop_dist

leverage_raw = (position_size * entry_price) / margin_used

leverage =
  clamp(
    leverage_raw
    * tier_multiplier
    * liquidity_multiplier,
    1,
    user_max_leverage
  )
```

#### 5.4.2 SL / TP dinamici (baseline)

- SL iniziale strutturale + buffer
- Break-even a R ≥ 1
- Scale-out:
  - 50% @ R1
  - 30% @ R2
- Trailing:
  - swing oppure ATR (uno solo)
- Kill-switch:
  - spread explode
  - book collapse
  - funding + OI shock
  - quality gate fail

## 6. Execution Engine (Railway Worker)

Responsabilità:

- place / cancel / modify
- idempotenza
- retry controllati
- stato ordini coerente
- stop immediato se Gate 0 fallisce

## 7. AI — dove entra (senza rompere nulla)

**Ammesso**

- sentiment/news → feature
- anomaly detection
- suggerimenti (non vincolanti)
- explainability UI

**NON ammesso**

- modifica diretta di leva / SL / TP
- decisione finale di trade

AI = copilota, non pilota.

## 8. Audit & Replay (operativo, non accademico)

**Obiettivo pratico:** auditabilità solida senza replay bit‑perfetto del L2.

Si salva il minimo necessario per spiegare e ricostruire la decisione in modo affidabile,
accettando che il replay sia **logico** (non identico al tick).

**Ogni trade salva:**

```json
{
  "trade_id": "uuid",
  "strategy_version": "v1.0",
  "feature_snapshots": ["id1", "id2"],
  "decision": {...},
  "orders": [...],
  "execution_metrics": {...}
}
```

Deve essere riproducibile in demo.

## 9. Test Path (senza auto-inganni)

- Replay deterministico (features storiche)
- Binance Futures Demo
- Shadow trading (real market, no execution)
- Real con size minima

## 10. Stack (best practice 2025)

- Supabase: Auth, DB, Vault, RLS
- Railway: API + Worker + WS
- Vercel: UI
- Groq: AI inference low-latency (solo feature/advisory)

### 12.2 Tabelle core (users, profiles, settings)

  updated_at timestamptz not null default now(),

before update on public.profiles
for each row execute function public.set_updated_at();

on public.profiles for select
using (auth.uid() = user_id);

create policy "profiles_update_own"
on public.profiles for update
using (auth.uid() = user_id)

## 14. Prompt completo per VS Code Agent (build end-to-end)

Copia/incolla così com’è al tuo agente VS Code.

Sei un senior full-stack engineer 2025. Obiettivo: rendere operativo un sistema deterministico per trading Binance Futures con Supabase+Vercel+Railway, senza refactor futuri quando aggiungeremo nuove fonti (L2, options, AI).

Repo: monorepo con apps/web (Next.js), apps/api (Fastify), apps/worker (Node worker), packages/shared.

**PRIORITÀ ASSOLUTE:**
1) Security & Secrets: API key Binance per-user NON devono mai arrivare in chiaro al frontend oltre l’onboarding; vanno salvate in Supabase Vault e lette solo da API/Worker con service-role.  
2) Determinismo: Strategy Kernel produce TradePlan in JSON versionato, auditabile; AI può solo fornire features/advisory.  
3) OMS robusto: idempotenza, retry controllati, stato coerente.  
4) Free data only: usare solo API gratuite (Binance market + derivatives + L2 via websocket; CoinGecko opzionale per context).

### TASK A — SUPABASE DB + RLS + VAULT

- Implementa lo schema SQL indicato in RFC: profiles, exchange_connections, symbol_universe, feature_snapshots, trade_plans, jobs, executions + triggers updated_at.
- Abilita RLS e policy "own rows" per user_id.
- Prepara uno script di bootstrap (supabase/migrations/...) con DDL.
- Prepara endpoint API per:
  - POST /v1/connections/binance  (salva segreto in Vault e metadata in exchange_connections)
  - GET  /v1/connections
  - DELETE /v1/connections/:id

### TASK B — API (Fastify su Railway)

- Integra Supabase Auth: middleware che valida JWT utente e ricava user_id.
- Implementa endpoints:
  1) GET /v1/universe (permette read)
  2) POST /v1/plans/build  -> crea TradePlan deterministico (Kernel v1) usando ultime FeatureSnapshots (o placeholder se collector non pronto)
  3) POST /v1/plans/:planId/queue -> crea Job EXECUTE_PLAN
  4) GET /v1/plans (list own)
  5) GET /v1/executions (list own)
- Il build del TradePlan deve includere Gate0..3 e calcolo deterministico di qty/leverage/SL/TP con clamp tier.

### TASK C — WORKER (Railway)

- Implementa job runner:
  - poll jobs QUEUED in DB, lock atomico (locked_at, locked_by), set RUNNING.
  - per EXECUTE_PLAN:
    - carica TradePlan, carica exchange_connection
    - recupera segreto da Vault (apiKey/apiSecret)
    - esegue ordine su Binance Futures Demo (is_testnet=true) con endpoint REST corretti
    - crea record executions + aggiorna trade_plans.state
    - posta Job MONITOR_POSITION
  - per MONITOR_POSITION:
    - controlla posizione, aggiorna SL/TP dinamici se regole triggerate (BE/trailing/kill-switch)
- Implementa idempotency: se job già processed o exec già creato, non duplicare ordini.

## 16. Rate-limit policy Binance + Backoff + Circuit Breaker

### 16.1 Cosa monitorare (headers/limiti)

Per Futures, Binance espone:

- IP weight usage via `X-MBX-USED-WEIGHT-1M` (e simili)
- Order count usage via `X-MBX-ORDER-COUNT-10S` e `X-MBX-ORDER-COUNT-1M` su endpoints trade
- Se prendi 429 e continui, rischi 418 ban; arriva spesso `Retry-After` che devi rispettare
- Futures default (doc Binance FAQ): 2400/min IP e 1200/min order per account/subaccount

### 16.2 Strategia generale (HFT-like senza ban)

Regola d’oro: usare WS per market-data e ridurre polling REST al minimo. Binance stessa consiglia WS per live updates per evitare weight e ban.

**Budgeting (token bucket doppio)**

Mantieni 2 bucket:

- `IP_WEIGHT_BUCKET` (cap ~2000/1m)
- `ORDER_BUCKET` (cap ~900/1m + ~40/10s)

Aggiorna i bucket leggendo gli header a ogni risposta (server-truth).

### 16.3 Backoff: 429 / 418 / 5xx

**Se 429 (rate limit)**

- leggi `Retry-After` se presente e dormi quel numero di secondi
- se non presente: exponential backoff con jitter:

```
1s, 2s, 4s, 8s (max 30s) + jitter 0–250ms
```

- riduci “non-critical traffic” (universe refresh, extra snapshots)

**Se 418 (auto-ban)**

- stop totale verso Binance per `Retry-After` secondi (obbligatorio)
- apri circuit breaker “OPEN”

**Se 5xx / timeouts**

- backoff più leggero (250ms→2s) + retry max 3
- se supera soglia errori in finestra → circuit breaker “HALF-OPEN”

### 16.4 Circuit breaker (3 stati)

Per ogni “route group”:

- `public_marketdata_rest`
- `private_trade_rest`
- `private_account_rest`
- `ws_trading` (se lo usi)
- `ws_marketdata`

**CLOSED:** normale  
**OPEN:** blocca richieste per cooldown (es. 30–120s o Retry-After)  
**HALF-OPEN:** consente 1–3 richieste di test; se ok → CLOSED, se fail → OPEN

**Trigger tipici:**

- 2× 429 in 60s → OPEN 60s
- 1× 418 → OPEN per `Retry-After`
- error rate 5xx > 30% su 20 richieste → OPEN 30s

### 16.5 WebSocket limits (market streams)

Non confondere: il limite “5 msg/sec” riguarda i messaggi in uscita dal client (subscribe/unsubscribe/ping/pong), non gli eventi che Binance ti push-a.

Altri limiti utili:

- max 1024 streams per connessione
- max 300 tentativi connessione / 5 min / IP

**Policy consigliata**

- fai pochi WS, lunghi, stabili
- subscribe batch, non “subscribe/unsubscribe a raffica”
- heartbeat/ping a intervalli ragionevoli (rispetta 5/sec)

### 16.6 Endpoint weights: cosa evitare

- preferisci WS per prezzi/klines/OB
- su REST, evita polling multi-symbol pesante
- per ordini multipli puoi usare `batchOrders` ma pesa di più in IP weight e order count (es. weight 5)

Quindi: batch solo quando serve davvero, e sempre dentro order-bucket.

### 16.7 Checklist di implementazione (rapidissima)

In ogni risposta Binance REST, salva in memoria:

- `x-mbx-used-weight-1m`
- `x-mbx-order-count-10s`, `x-mbx-order-count-1m` (se presenti)

Prima di ogni chiamata:

- se used_weight > soft_threshold → degrada (stop polling)
- se used_weight > hard_threshold → blocca non-critici
- se order-count vicino limite → stop modifiche/refresh ordini non essenziali

**429/418**

- rispetta `Retry-After` sempre

**WS**

- max 1–2 connessioni per market streams, sotto 1024 streams
- throttle subscribe/unsubscribe (≤5 msg/sec)
